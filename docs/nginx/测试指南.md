# 多模型路由 · 部署与测试指南

> 配套设计：[2026-08-19-multi-model-routing-design.md](../superpowers/specs/2026-08-19-multi-model-routing-design.md)
> nginx 参考配置：[docs/nginx/llm-routing.example.conf](llm-routing.example.conf)
> 适用场景：B 机 nginx 多模型路由 + C 机 modelctl 网关（model 参数路由）

## 0. 架构速览

```
A 设备（cc-switch / OpenAI SDK）  —— /v1* 一律需要凭据：Authorization: Bearer <key> 或 x-api-key: <key>
        │ https（自建 CA，见 tls-setup.md；旧 http:// 客户端切换后立即失败）
        ▼
B 机 nginx :5000（listen ssl + 凭据白名单校验 + 限流 → 429）
        │
        ├── /210/llm/<模型>/v1/...         路径式直连 → C 机模型端口（如 18888）
        │      凭据：该模型 profile api_key（nginx 不改写 Authorization，引擎直接校验）
        ├── /210/llm/<模型>/v1/api/usage   按模型用量 → C 机 :5002
        │      凭据：客户端 key 或任一 profile key
        ├── /210/llm/v1/...                统一网关 → C 机 :5003（按 body.model 分发）
        │      凭据：仅 GATEWAY_CLIENT_API_KEY（网关再改带 profile key 认证上游）
        └── /210/llm/v1/api/usage          旧用量（兼容旧卡片）→ C 机 :5002
               凭据：客户端 key 或任一 profile key
```

模型注册表单一来源 = `models/*.yaml`；nginx map 片段由 `modelctl nginx-snippet` 生成。

> **模型名 = profile 的 `name` 或其 `alias`**。当前 llamacpp 模型已配置短名别名：
> `deepseek-v4-flash-llamacpp` ↔ `deepseek-v4-flash`、`qwen3.8-llamacpp` ↔ `qwen3.8`。
> URL 路径、网关 `model` 参数、用量 `?model=` 均可用长名或短名。

> 已为 gateway 单独建子项目（`gateway/pyproject.toml`，落到 `.venvs/gateway`）：
> 首次 `modelctl gateway start` 时自动 `uv sync --project gateway`，主项目 `uv sync` 不会清掉它。

## 1. 部署服务器（C 机）配置

```bash
# ① 安装网关依赖（fastapi / uvicorn / httpx，独立子项目，不落主 lockfile）
cd /path/to/modelctl && uv sync --extra dev && modelctl env setup gateway

# ② .env 追加（参考 .env.example）
NODE_ID=210
NODE_HOST=192.168.77.210
GATEWAY_HOST=0.0.0.0
GATEWAY_PORT=5003
GATEWAY_DEFAULT_MODEL=deepseek-v4-flash
GATEWAY_READ_TIMEOUT=600
# 数据面客户端密钥（必配）：留空 ⇒ fail-closed，网关 /v1* 全部 401
# 生成：python -c "import secrets;print('sk-'+secrets.token_urlsafe(32))"
GATEWAY_CLIENT_API_KEY=sk-xxxx

# ③ 确认模型已启动（deepseek-v4-flash-llamacpp → 18888）
modelctl status

# ④ 启动用量统计服务（用量路由依赖 5002）
modelctl stats start

# ⑤ 启动网关
modelctl gateway start
modelctl gateway status        # 期望：网关：运行中，/v1/models 正常

# ⑥ 本地验证网关（不经 nginx，直连 C 机；/v1* 同样需要客户端 key）
curl -s http://127.0.0.1:5003/v1/models -H "Authorization: Bearer $GATEWAY_CLIENT_API_KEY"
curl -s http://127.0.0.1:5003/v1/chat/completions \
  -H "Authorization: Bearer $GATEWAY_CLIENT_API_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-v4-flash","stream":false,"messages":[{"role":"user","content":"hi"}]}'

# ⑦ 生成 nginx map 片段（供 B 机使用；输出含 name 与 alias 两条目 + 凭据校验 map）
#    自动读 .env 的 GATEWAY_CLIENT_API_KEY（也可显式 --client-key）；未配置则不生成鉴权片段
modelctl nginx-snippet --node 210 --host 192.168.77.210
```

注意事项：

- 防火墙需放行 `5003`（网关）、`5002`（统计）、模型端口（如 `18888`）给 B 机。
- 新增模型流程：新增一条 profile → `modelctl start <name>` → 重新执行 ⑦ 生成片段 → 更新 B 机 `/etc/nginx/conf.d/llm-routes-210.conf`。

### 1.1 启动顺序与自检

完整启动顺序（首次部署或全部重启）：

```bash
modelctl status                 # ① 模型（逐个 modelctl start <name>）
modelctl stats start            # ② 用量统计（依赖模型 /metrics）
modelctl gateway start          # ③ 网关
```

自检清单：

| 检查项 | 命令 | 期望 |
|---|---|---|
| 模型健康 | `curl -s http://127.0.0.1:18888/health` | 200 |
| 模型指标 | `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:18888/metrics -H "Authorization: Bearer $API_KEY"` | 200 |
| stats 用量 | `curl -s "http://127.0.0.1:5002/api/usage?model=deepseek-v4-flash"` | `"isValid": true` |
| 网关模型列表 | `curl -s http://127.0.0.1:5003/v1/models -H "Authorization: Bearer $GATEWAY_CLIENT_API_KEY"` | JSON 模型列表 |

> llama-server 必须带 `--metrics` 启动才提供 `/metrics`（modelctl 的 llamacpp 适配器已内置该参数，但**旧进程需重启才生效**）；`/metrics` 与 `--api-key` 同时启用时需鉴权头，stats 服务会自动带 key，手动 curl 需自行带 `Authorization: Bearer $API_KEY`。
>
> `modelctl status` / `modelctl gateway start` 会用 `GATEWAY_CLIENT_API_KEY` 探测 `/v1/models`；未配置该键时会直接提示"未配置 GATEWAY_CLIENT_API_KEY"，此时网关 /v1* 必然 401（fail-closed，属预期）。

### 1.2 更新代码后重启

`git pull` 拉取新代码后，**常驻服务不会自动加载新代码**，需手动重启：

```bash
modelctl stats stop && modelctl stats start            # stats（如指标采集相关修复）
modelctl gateway stop && modelctl gateway start        # 网关（如别名/路由相关修复）
bash script/modelctl.sh restart deepseek-v4-flash-llamacpp   # 模型（启动参数变更时，如 --metrics）
```

> `modelctl status` 只反映进程存活，不代表已加载新代码；模型启动参数（profile 改动）必须重启模型进程才生效。

### 1.3 上下文长度语义（各引擎）

所有引擎的上下文参数均表示**每个并发请求完整可用的上下文**（与并发数无关）：

| 引擎 | 参数 | 语义 | KV 显存 |
|---|---|---|---|
| llamacpp | `ctx_size` | 单请求上下文（启动总量 = ctx_size × parallel） | ≈ 并发 × ctx_size |
| ollama | `context_length` | 单请求上下文窗口 | ≈ 并发 × context_length |
| vllm | `max_model_len` | 单序列最大长度 | 按 max_num_seqs × max_model_len 估算 |
| sglang | `context_length` | 单序列上下文上限 | ≈ 并发 × context_length |
| unsloth | `context_length` | 单请求上下文 | ≈ 并发 × context_length |

要点：

- **语义统一**：`ctx_size` / `context_length` / `max_model_len` 都是"单请求可用上下文"，配置多少每个并发请求就能用多少——**并发只决定同时处理多少请求，不削减单请求上下文**。
- **llamacpp 实现差异**：llama-server 的 `--ctx-size` 是槽位共享的总量，modelctl 会自动用 `ctx_size × parallel` 作为启动总量，保证每个槽都能用满配置值（无需用户换算）。
- **KV 显存**：各引擎都随并发数线性增长（≈ 并发 × 单请求上下文）；显存紧张时优先调低并发而非削减上下文。

## 2. nginx 服务器（B 机）配置

> **为什么放 `conf.d/` 而不是 `sites-available/`**：`map` 指令属于 **http 块级**配置，而 `sites-available/` + `sites-enabled/` 的约定是存放 **server 块（虚拟主机）**。`/etc/nginx/conf.d/*.conf` 已被 nginx.conf 默认 include，是存放 http 级片段的惯例位置——**无需建新目录、无需改 nginx.conf**。

```bash
# ①（可选）确认 nginx.conf 已 include conf.d：grep include /etc/nginx/nginx.conf
# ② 在 C 机生成片段并上传（C 机执行 1-⑦；产物含明文密钥，上传后 chmod 600，严禁入库）
modelctl nginx-snippet --node 210 --host 192.168.77.210 > llm-routes-210.conf
scp llm-routes-210.conf root@B机IP:/etc/nginx/conf.d/
ssh root@B机IP 'chmod 600 /etc/nginx/conf.d/llm-routes-210.conf'

# ③ 数据面启用 TLS：按 docs/nginx/tls-setup.md 生成自建 CA + 服务端证书，
#    server 块改为 listen 5000 ssl + ssl_certificate*（一刀切，不留 http 监听）
```

### 2.1 nginx.conf（http 块）

无需修改——`include /etc/nginx/conf.d/*.conf;` 已存在于 http 块内，上传的 map 片段自动加载。

（若你的 nginx.conf 未 include conf.d，则手动加入该行，或改用独立目录并在 http 块 include。）

### 2.2 sites-enabled/myflaskapp（server 块）

删除原两条规则：

```nginx
location ~ ^/210/llm/(.*)$ { ... }              # 旧 LLM 主流量 → 18888
location ~ ^/210/llm/v1/api/usage(.*)$ { ... }  # 旧用量 → 5002
```

替换为 4 条新 location（**顺序固定不可乱**，完整示例见 `docs/nginx/llm-routing.example.conf`）：

| 顺序 | 用途 | 正则 | 转发目标 | 凭据白名单 |
|---|---|---|---|---|
| 1 | 旧用量（兼容旧卡片） | `^/(\d+)/llm/v1/api/usage(.*)$` | `:5002/api/usage$2` | `$llm_reject_all` |
| 2 | 按模型用量 | `^/(?<node_id>\d+)/llm/(?<model_name>[^/]+)/v1/api/usage$` | `:5002/api/usage?model=$model_name` | `$llm_reject_all` |
| 3 | 网关（model 参数） | `^/(?<node_id>\d+)/llm/(?<llm_rest>v1(?:/.*)?)$` | `:5003/$llm_rest`（**保留 v1/ 前缀**） | `$llm_reject` |
| 4 | 模型直连 | `^/(?<node_id>\d+)/llm/(?<model_name>[^/]+)/(?<llm_rest>.*)$` | map 注册表命中端口；未知 404 | `$llm_reject_all` |

关键点：

- **每个 location 先校验凭据再限流**：不在对应白名单 → 直接 `return 401`（OpenAI 错误信封）；命中 `limit_req`（30r/m burst=60）或 `limit_conn`（16）→ 429。两组白名单的分工见 3.1。
- **顺序即优先级**：网关规则（`v1`）必须**声明在**直连规则（`<模型>/`）**之前**——正则 location 按声明顺序匹配，若直连在前，`/llm/v1/...` 会被误判为模型名 `v1` 而走直连（转发到 18888 而非网关 5003）。
- **location 3 必须捕获并保留 `v1/` 前缀**（`(?<llm_rest>v1(?:/.*)?)`），否则转发到网关的路径缺少 `/v1`，网关返回 404；`(?:/.*)?` 让裸 `/llm/v1`（无尾斜杠，部分客户端 baseUrl 指向 `/llm` 时产生）也命中网关，避免误入规则 4 或兜底 location。
- location 4 通过 `rewrite ^/\d+/llm/[^/]+/(.*)$ /$1 break;` 剥离 `/<node>/llm/<模型>` 前缀，保留 `/v1/...` 转发给模型。
- 网关与模型直连均需关闭缓冲保证 SSE 流式：`proxy_buffering off;`（网关另加 `proxy_cache off;`、`X-Accel-Buffering no`）。
- 网关与直连均需 `proxy_read_timeout 600s; proxy_send_timeout 600s;`——llama-server 长响应超过 nginx 默认 60s 会被掐断（报 `upstream prematurely closed connection`）。
- 通用代理头（Host / X-Real-IP / 超时）已在 nginx.conf http 块定义，location 内无需重复。

## 3. 客户端测试

### 3.1 curl 校验矩阵（先导出下方变量；Windows 见本节末尾）

> **鉴权说明（重要，行为已变更）**：
> - **所有 /v1 路径都需要凭据**，可带 `Authorization: Bearer <key>` 或 `x-api-key: <key>`（Anthropic 客户端只带后者）。
> - **网关路径**（`/<node>/llm/v1/...`）：带 `GATEWAY_CLIENT_API_KEY`。该 key 仅用于准入，
>   网关会改用后端 profile key 认证上游，客户端无需知道 profile key。
> - **模型直连路径**（`/<node>/llm/<模型>/v1/...`）：带该模型的 `api_key`（profile key）。
>   nginx 不改写 Authorization，引擎直接校验该值，因此必须用 profile key 而非客户端 key。
> - nginx 白名单**同时包含** `GATEWAY_CLIENT_API_KEY` 与全部 profile `api_key`，
>   两条路径各有可用组合，既有客户端无需改造。
> - 缺凭据 / key 不在白名单 → 401 `{"error":{"type":"authentication_error"}}`；命中限流 → 429。
> - 服务端未配置 `GATEWAY_CLIENT_API_KEY` → 网关 fail-closed，/v1* 一律 401（message 含 `not configured`）。
>
> 两条路径的凭据分工（运维最容易踩的点）：
>
> | 客户端携带 | 网关路径 `/<n>/llm/v1/...` | 直连路径 `/<n>/llm/<模型>/v1/...` |
> |---|---|---|
> | `GATEWAY_CLIENT_API_KEY` | **200**（nginx `$llm_reject` 放行 + 网关准入通过） | **200**（nginx `$llm_reject_all` 放行；引擎侧无 key 的 Ollama 等直接服务）—— 注：vLLM/llamacpp 等有 key 的引擎会 401 |
> | profile `api_key` | **401**（nginx `$llm_reject` 只含客户端 key，直接拒绝） | **200** |
>
> 两组白名单的分工：`$llm_reject` 只含 `GATEWAY_CLIENT_API_KEY`，与网关 `verify_client` 同口径；`$llm_reject_all` 额外含各 profile `api_key`，因为直连 location 不改写 `Authorization`，vLLM/SGLang 等引擎只认 profile key。带客户端 key 走直连路径，对有 key 的引擎会 401（引擎不认）——想让两条路径一把 key 通吃，可把 `GATEWAY_CLIENT_API_KEY` 配成与 profile `api_key` 相同值（会失去数据面/管理面隔离，不推荐）。

```bash
# 变量定义（复制执行前先导出；Windows PowerShell 用 $env:CLIENT_KEY，见本节末尾）
export CLIENT_KEY="<GATEWAY_CLIENT_API_KEY 的值>"
export PROFILE_KEY="<该模型 profile 的 api_key，即 C 机 .env 的 API_KEY>"
export B=<B机地址>            # 如 36.156.121.146
export NODE=210
# 未把 ca.crt 导入系统信任库时，所有 curl 追加 -k（见 tls-setup.md §3，属安全降级）

# ① 路径式直连-模型列表（直连必须带 profile key）
curl -s https://$B:5000/$NODE/llm/deepseek-v4-flash/v1/models \
  -H "Authorization: Bearer $PROFILE_KEY"

# ② 路径式直连-对话（直连必须带 profile key）
curl -s https://$B:5000/$NODE/llm/deepseek-v4-flash/v1/chat/completions \
  -H "Authorization: Bearer $PROFILE_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-v4-flash","stream":false,"messages":[{"role":"user","content":"你好"}]}'

# ③ 网关-缺省 model（回退默认模型，旧卡片行为不变；带客户端 key）
curl -s https://$B:5000/$NODE/llm/v1/chat/completions \
  -H "Authorization: Bearer $CLIENT_KEY" \
  -H 'Content-Type: application/json' -d '{"messages":[{"role":"user","content":"你好"}]}'

# ④ 网关-显式 model 切换（带客户端 key）
curl -s https://$B:5000/$NODE/llm/v1/chat/completions \
  -H "Authorization: Bearer $CLIENT_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"你好"}]}'

# ⑤ SSE 流式（-N 逐块输出，验证 token 即时推送；直连必须带 profile key）
curl -N -s https://$B:5000/$NODE/llm/deepseek-v4-flash/v1/chat/completions \
  -H "Authorization: Bearer $PROFILE_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-v4-flash","stream":true,"messages":[{"role":"user","content":"讲个笑话"}]}'

# ⑥ 旧用量（兼容旧卡片；客户端 key 或 profile key 均可）
curl -s "https://$B:5000/$NODE/llm/v1/api/usage" \
  -H "Authorization: Bearer $CLIENT_KEY"

# ⑦ 按模型用量（客户端 key 或 profile key 均可）
curl -s "https://$B:5000/$NODE/llm/deepseek-v4-flash/v1/api/usage" \
  -H "Authorization: Bearer $CLIENT_KEY"

# ⑧ 未知模型路径 → 期望 404（凭据合法；带 profile key 亦可——nginx 先验凭据后查 map）
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Authorization: Bearer $CLIENT_KEY" \
  https://$B:5000/$NODE/llm/ghost-model/v1/models

# ⑨ 缺凭据 → 401（网关路径）
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://$B:5000/$NODE/llm/v1/chat/completions \
  -H 'Content-Type: application/json' -d '{"messages":[{"role":"user","content":"hi"}]}'

# ⑩ x-api-key 通道同样可用
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  https://$B:5000/$NODE/llm/v1/chat/completions \
  -H "x-api-key: $CLIENT_KEY" -H 'Content-Type: application/json' \
  -d '{"model":"deepseek-v4-flash","messages":[{"role":"user","content":"你好"}]}'
```

预期结果：

| 用例 | 期望 |
|---|---|
| ①-④ | 200，正常 JSON（模型名被正确改写/回退） |
| ⑤ | 200，token 逐块输出（SSE） |
| ⑥⑦ | 200，cc-switch 兼容用量 JSON |
| ⑧ | 404 |
| ⑨ | 401，`{"error":{"type":"authentication_error"}}` |
| ⑩ | 200（`x-api-key` 与 Bearer 同权） |

> - 直连 ① 带客户端 key（而非 profile key）时，llama-server/vllm 返回 `401 Invalid API Key`，属正常（见上方矩阵）。

### 3.3 OpenAI 兼容 SDK

```python
import httpx
from openai import OpenAI

client = OpenAI(
    base_url="https://xxx:5000/210/llm/v1",   # 网关；或直连 /210/llm/deepseek-v4-flash/v1
    api_key="sk-xxxx",                        # 网关路径：GATEWAY_CLIENT_API_KEY；直连路径：该模型 profile api_key
    # 未把 ca.crt 导入系统信任库时指定 CA 文件（降级 verify=False 属安全降级，见 tls-setup.md §3）：
    http_client=httpx.Client(verify="/path/to/ca.crt"),
)
resp = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": "你好"}],
    stream=True,
)
for chunk in resp:
    print(chunk.choices[0].delta.content or "", end="", flush=True)
```

## 4. 排错速查

| 现象 | 排查方向 |
|---|---|
| `401 authentication_error` | 未带 key / key 不匹配 / 服务端未配 `GATEWAY_CLIENT_API_KEY`。看网关日志 `auth=missing\|invalid\|unconfigured` 区分三档；`modelctl status` 会直接提示"未配置 GATEWAY_CLIENT_API_KEY"。注意：网关路径只认 `GATEWAY_CLIENT_API_KEY`（profile key 会被 nginx `$llm_reject` 拒），直连路径要带 profile key（见 3.1 矩阵） |
| `429` | 命中 `limit_req`（30r/m burst=60）或 `limit_conn`（16）。单 IP 退避重试；确属多人共用出口 IP，按 `llm-routing.example.conf` 注释调高 zone 速率 |
| TLS 握手失败 / 连接重置 | 客户端仍用 `http://`，或 https 客户端未信任 CA 且未加 `-k`/`verify`（见 tls-setup.md） |
| 直连路径返回 `401 Invalid API Key`（引擎报文） | nginx 已放行但引擎不认该 key：客户端带了客户端 key 而非该模型 profile `api_key`（llama-server/vllm 强制校验） |
| 用量报 `HTTP Error 404: Not Found` | ① llama-server 未带 `--metrics`（旧进程 → 重启模型）；② stats 服务为旧代码（曾存在 `/metrics/metrics` 双重拼接 bug → `git pull` 后重启 stats） |
| 手动测 `/metrics` 返回 401 | 需带 `Authorization: Bearer <API_KEY>`（stats 服务内部会自动带） |
| 更新代码后行为未变 | 常驻服务（stats/gateway）未重启；`git pull` 后需 `modelctl stats stop && start`、`modelctl gateway stop && start` |
| ③④ 网关路径 502 | C 机网关未启动（`modelctl gateway status`）或独立 venv 未创建（`modelctl env setup gateway`） |
| ① 直连 502 / 超时 | 模型未启动（`modelctl status`）；防火墙未放行模型端口 |
| 网关路径 404 | B 机 location 3 未保留 `v1/` 前缀（需应用修复后的配置） |
| 未知模型名非 404 | location 4 的 `return 404` 缺失或被其他 location 抢占 |
| 用量无数据 / 显示错误 | C 机统计服务未启动（`modelctl stats start`）；或模型无 Prometheus 指标（ollama 不支持精确统计） |
| 新增模型后直连 404 | 未重新生成并上传 map 片段（`modelctl nginx-snippet` → B 机 `/etc/nginx/conf.d/` → reload） |
| 流式不推送（一次性返回） | 网关/直连 location 缺 `proxy_buffering off;` |
