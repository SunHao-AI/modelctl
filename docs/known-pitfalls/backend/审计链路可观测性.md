# 请求审计链路可观测性（失败留痕 + 前后端契约）

> 2026-09-10：沉淀「调用记录」能力落地时发现的三类问题——失败请求完全无痕、审计读写两端字段各写各的、以及改多分支同构代码时的定位陷阱。

## 404 / 上游 4xx / 502 三类失败请求审计零留痕，"调用记录"只记得住成功

**日期**：2026-09-10
**症状**：网关号称有请求级 JSONL 审计，但排查"某个客户端一直报错"时翻当日审计文件，**一条记录都没有**——只有成功请求落了盘。

**根因**：`gateway.py` 里 `audit_log.record(...)` 只挂在正常返回路径上。三条失败路径提前 `return`，绕过了所有落盘点：

1. 模型名解析失败 → 直接返回 404，未 record；
2. 上游返回 4xx（非流式与流式各一处）→ 直接把上游响应透传，未 record；
3. 连接后端异常 → `except` 里返回 502，未 record。

失败请求恰恰是最需要留痕的，"只记成功"的审计在排障时等于没有。

**解决方案**：三条路径各自补 `audit_log.record(_build_audit_entry(...))`，并保留请求里的**原始 model 拼写**（不是解析后的 profile 名），这样"用户把 `qwen3` 拼成 `qwen-3`"这类问题才能从审计里看出来。上游 4xx 把响应体截 500 字写进 `error` 字段。OpenAI 与 Anthropic 两条代理路径同口径补齐。

**教训**：

- **审计/日志/计量这类横切关注点，必须逐条走查所有 `return` 出口**，不能只在"主流程末尾"挂一次。函数里每个 `return` 都要问一句"这条路径留痕了吗"。
- 失败路径留痕要记**输入原貌**而非归一化后的值：归一化恰恰掩盖了失败原因。
- 用 `_read_audit_records(tmp_path)` 这类"直接读落盘 JSONL"的断言来钉审计，比 mock `record` 调用更可靠——mock 只证明"调了"，读文件证明"记对了内容"。

## 审计读写两端字段各写各的：参数不认、字段名分裂、响应缺字段，四处全部静默失效

**日期**：2026-09-10
**症状**：Web UI 审计页功能看起来"接好了"，实际四处静默失效——级别筛选选了没用、端点筛选选了返回空、"错误数"卡片恒为 0、"近 14 天"柱状图恒显示"无数据"。

**根因**：写入侧 `gateway._build_audit_entry`、读取侧 `webui/admin_audit.py`、前端 `web/src/api/audit.ts` + `AuditLogView.vue` 三端各自演进，无人对齐：

| 前端发出/读取 | 后端实际 | 后果 |
|---|---|---|
| 传 `level`、`keyword` 查询参数 | `read_audit` 签名里根本没有这两个参数 | FastAPI 忽略未知 query，过滤恒不生效 |
| 读 `list.error_count` | 响应只有 `entries` | 卡片 `?? 0` 兜底成 0，看不出是没数据还是没接上 |
| 读 `stats.by_day` 数组 | `/stats` 只返回 `{total, errors, by_model}` | 柱状图 `?? []` → 恒"无数据" |
| `endpoints` 过滤读 `entry["endpoint"]` | 写入侧落的是 `path` 键 | 取值恒 `None`，选任何端点都返回空 |
| `auditCleanup(days)` 把 `days` 放 query | 后端从 JSON body 读 | 永远按环境变量 30 天清理 |
| 展示 `size_mb` 语义 | 后端返回的是**字节整除 MB** | 小文件清理后恒显示 0.0 MB |

**解决方案**：以后端为唯一口径，逐项补齐并在两侧各钉测试：

- `read_audit` 新增 `level` / `keyword` 参数；JSONL 里**没有 level 字段**，由后端按 `status_code` 派生（5xx→error、4xx→warn、其余 info）并**注入返回的每条 entry**，前端列表列与过滤器因此共用同一口径；
- 响应补 `total` / `error_count`，且**必须在 `limit` 截断前统计**（否则"错误数"随 limit 变化）；
- `/stats` 补 `by_day: [{date,total,error}]`（按分片文件所属日聚合，画图够用，避免为画图逐行全扫）并接受与列表同源的 `since`；
- `endpoints` 过滤改成先读 `path`、回退读 `endpoint`（兼容旧格式分片）；
- `/cleanup` 接受 body 里的 `days`，响应同时给 `removed` / `freed_bytes` / `size_mb` / `deleted`，`dry_run` 也统计预计释放量。

**教训**：

- **前端 `?? 0` / `?? []` 这类兜底会把"契约错位"伪装成"暂无数据"**——是最难发现的一类 bug。新接一个端点时，先断言后端响应里真的有前端读的那个键。
- 未知 query 参数被 FastAPI **静默忽略**（不报 422），所以"前端传了后端不认"没有任何噪音。跨端加过滤参数时，两侧都要钉测试：后端钉"传该参数结果确实变窄"，不能只钉前端调用形状。
- **读写同一份持久化数据（JSONL/DB）时，键名必须有一处单一事实来源**。这里写入侧用 `path`、读取侧用 `endpoint`，中间没有任何一层能发现分裂。
- 派生字段（如 level）由**后端统一算**并随响应下发，别让前端各算各的，否则列表列与过滤器很容易用两套口径。

## 多分支同构代码：文本相同的 SearchReplace 会落到错误分支

**日期**：2026-09-10
**症状**：给 OpenAI 代理路径补 502 审计后，`test_audit_records_backend_unreachable` 报 `IndexError: list index out of range`——审计文件是空的，改动"没生效"。

**根因**：`err_msg = f"后端不可达：{error}"` 这一行在 `proxy()`（OpenAI）和 `anthropic_proxy()` 两个函数里**逐字符相同**，`SearchReplace` 命中了先出现的 anthropic 分支。改动确实落了盘，只是落错了函数。

同类问题第二次出现：给 anthropic 分支补审计时照抄了 `path=path`，而 `anthropic_proxy()` **没有 `path` 形参**（它固定处理 `messages`），运行时才 `NameError`。

**解决方案**：

- 用**分支独有上下文**做锚点（如 OpenAI 分支里紧随其后的 `if admin:`），而不是两分支共有的文本；
- 改完立刻用 `Grep` 确认目标行号落在预期的函数区间内；
- 改多分支时**两条分支都补**（anthropic 原本也缺 502 审计），并各钉一条用例（`path == "messages"` 直接暴露形参不存在）。

**教训**：

- 在有两个同构代理函数的文件里改动，**"替换成功"不等于"替换到了要改的那处"**。必须用能唯一定位的上下文，改完回读确认。
- 复制另一分支的代码时，**逐个核对形参是否存在**——同名变量在不同函数里的可得性不同。
- 每条新分支路径都要有自己的用例；只测一条分支时，另一条的照抄改动无人看守。
