# 错误分类与修复引导

> 本文件为 WebUI 启动失败提供环境创建入口（2026-09-07）沉淀问题的聚合入口；原始单文件已并入本文件归档以保留溯源信息。

## 失败提示指向 CLI 命令而 WebUI 已有同能力 —— 指向错误的一端；解法是结构化错误码贯通，勿正则解析文案

- **日期**：2026-09-07　**分类**：后端 / 错误分类

### 根因

引擎启动失败时，后端 detail 文案是复用 CLI 时代的编排层报错（如 `xx 专用环境未创建，执行：modelctl env setup xx`）。在纯 CLI 语境里这个提示是对的，但 WebUI 早就有同能力——环境页 `/envs` 可一键创建托管 venv、Docker 旁路区块可装 Docker——**用户却在任务失败卡片里只看到一句让它去敲命令的文案**。能力就在隔壁页面，提示却指向了错误的一端（CLI）。

最直觉的"修法"是前端对 detail 做正则/`includes` 匹配再决定显示什么按钮——这是把错误**文案**当契约。文案是给运维读的自然语言，改措辞、调标点都属于自由发挥，前端正则会在某次无害的文案修订后静默失效（匹配不上 = 按钮消失，无任何报错）。文案与机器可读标识必须分离。

### 解决方案

**后端结构化错误码贯通任务事件，前端按 code 渲染动作**，链路四层各钉一处：

1. **分类单点**（`core/cluster/reconcile.py`）：`classify_start_failure(detail, engine)` 复用既有 `_ERROR_RULES` 有序关键字表（单一关键字源，不另起炉灶），只在"命中首个规则 **且** 该码 ∈ `_ACTIONABLE_CODES`（`venv_missing` / `docker_missing`）"时返回 `(code, engine)`，否则 `(None, None)`。**宁缺毋滥**：端口冲突、OOM 等 WebUI 给不出修复入口的失败绝不挂码，避免渲染误导性按钮。engine 由调用方从 `profile.engine` 直传，不从 detail 猜。
2. **任务透传**（`webui/admin_tasks.py`）：`Task` 增可选字段 `code`/`engine`；`error()` 增 keyword-only 参数；`done` 事件 payload 与 `to_dict()` 均**条件加键**（仅携带时出现）——老前端拿到的 JSON 与旧版逐字节一致，向后兼容零成本。
3. **失败收尾**（`webui/admin_models.py`）：`_fail_task(task, exit_code, message, engine)` 统一入口，启动/重启全部失败路径（result error / RequirementError / 其它异常）收敛到一处挂码，杜绝漏改。
4. **前端按码渲染**（`web/src/stores/tasks.ts` + `TaskDrawer.vue`）：SSE `done`、轮询、刷新 `toRecord` **三路**都要透传 code/engine，漏任何一路则"刷新后按钮消失"；抽屉按 code 渲染——`venv_missing` 且本平台可建 → [创建环境]（直接提交 env_setup 任务复用全局任务链路）；`docker_missing` 或平台不可建 venv（Windows）→ [去环境页]（`/envs?focus=<engine>` 定位高亮）。

### 两个易踩的细节

- **`_ERROR_RULES` 顺序陷阱**：规则表是"首个命中即返回"的有序子串表，`("Docker 环境未就绪", "docker_missing")` **必须排在** `("环境未就绪", "venv_missing")` **之前**——前者字面包含后者，顺序颠倒则配了 `docker_image` 但 Docker 缺失的失败被判成 `venv_missing`，把 Windows 用户引导去建 Windows 上根本不可用的托管 venv。这与既有的 `[gpu_lock]` 须先于 `gpu_list` 是同一类"具体串必须先于被其包含的笼统串"约束，新增规则时先 grep 全表找包含关系。
- **`classify_error` 与 `classify_start_failure` 语义相反，别混用**：前者给集群中心做兜底归类，**必有值**（未命中 → `runtime_capability`，因为"环境能力不足"是未分类报错最常见真实原因，比 `unknown` 更能指导运维）；后者给 WebUI 渲染修复动作，**宁可无码不可错码**（未命中/不可操作 → `(None, None)`）。共享规则表但共享不了兜底语义。

### 代码示例

```python
# ✅ 后端：有序规则表——具体必须先于被它包含的笼统（reconcile.py）
_ERROR_RULES: tuple[tuple[str, str], ...] = (
    ("[gpu_lock]", "gpu_lock"),
    ...
    ("专用环境未创建", "venv_missing"),
    ("PATH 中找不到", "venv_missing"),
    ("Docker 环境未就绪", "docker_missing"),  # 必须早于"环境未就绪"
    ("未安装", "venv_missing"),
    ("环境未就绪", "venv_missing"),
    ...
)

_ACTIONABLE_CODES = frozenset({"docker_missing", "venv_missing"})

def classify_start_failure(detail: str, engine: str) -> tuple[str | None, str | None]:
    """与 classify_error 共享 _ERROR_RULES，但只在命中可操作码时才给码——宁缺毋滥。"""
    text = detail or ""
    for needle, code in _ERROR_RULES:
        if needle in text:
            return (code, engine) if code in _ACTIONABLE_CODES else (None, None)
    return (None, None)
```

```python
# ✅ done 事件 / to_dict 条件加键：不携带时 JSON 与旧版逐字节一致（admin_tasks.py）
payload = {"status": "error", "exit_code": exit_code, "message": self.detail, "task_id": self.id}
if code is not None:
    payload["code"] = code
if engine is not None:
    payload["engine"] = engine
self.event("done", payload)
```

```ts
// ✅ 前端按 code 渲染动作，绝不碰文案（TaskDrawer.vue）
function fixAction(t: TaskRecord): '' | 'setup' | 'goto' {
  if (t.status !== 'error' || !t.code) return '';
  if (t.code === 'docker_missing') return 'goto';
  if (t.code !== 'venv_missing' || !t.engine) return '';
  return platformMap.value[t.engine] ? 'setup' : 'goto';  // 平台能力懒加载，未到前保守降级 goto
}
```
