# 网关鉴权（主题聚合）

> 原始单文件已并入本文件归档（本主题为网关客户端鉴权 2026-09-07 首次沉淀，无历史归档）。

## 网关覆盖客户端 Authorization 导致"带了 key 也不校验"

- **日期**：2026-09-07　**分类**：后端 / 网关鉴权
- **现象**：数据面 `/v1/models`、`/v1/chat/completions` 等全部端点无任何凭据校验；客户端即使老实带了 `Authorization: Bearer <key>`，这个 key 也会被网关读取后**直接丢弃覆盖**，行为与不校验完全等价——任何知道 URL 的人可匿名白嫖 GPU。
- **根因**：转发时上游认证头以 profile 有效 key 为准，**无条件覆盖**客户端带来的头（`core/gateway.py` `proxy` 内 L933-942：`up_key = target.upstream_api_key()` 非空即 `headers["Authorization"] = f"Bearer {up_key}"`；`anthropic_proxy` L714-718 同理同时改写 `x-api-key` 与 `Authorization`）。这个"网关代填引擎 key"的设计本身是对的（客户端自配 key 可能与后端不一致，透传会导致 vLLM 401），但它掩盖了另一个问题：**准入**与**上游认证**是两件事，覆盖上游头之前没人对客户端 key 说过"是"。
- **解决方案**：准入与上游认证分离。新增 `verify_client()`（`core/gateway.py` L84-108）只做准入——`Authorization: Bearer <key>` 或 `x-api-key: <key>` 双通道嗅探比对 `GATEWAY_CLIENT_API_KEY`，**验完即丢**；上游照旧用 profile key（profile 无 key 则上游不带任何认证头，见下条）。三个处理器（`proxy` L870、`anthropic_proxy` L660、`list_models` L611）首行显式调用，未通过一律 401（OpenAI 错误信封）。审计覆盖有差别：两个 POST 处理器（`proxy` L874-880、`anthropic_proxy` L664-670）对被拒请求落审计（记 `auth=missing|invalid|unconfigured` 标签 + `client_ip`）；`GET /v1/models` 仅返回 401 **不落审计**（有意设计——它不是推理端点，无需按请求计费/留痕）。未配 key 时 fail-closed 全拒（`AUTH_UNCONFIGURED`），与 `all_service.py` 的运行提示同口径。
- **测试钉**：`tests/test_gateway.py::test_verify_client_bearer_ok` / `::test_verify_client_xapikey_ok` / `::test_verify_client_fail_closed_when_unconfigured`（fail-closed 用例必须 `setenv("")` 而非 `delenv`——`load_env()` 是 setdefault 语义，delenv 后会被本地 .env 读回来，用例结论随机器漂移）。

## "验完即丢"必须贯彻到上游转发——keyless profile 曾把准入 key 透传引擎

- **日期**：2026-09-07　**分类**：后端 / 网关鉴权
- **现象**：网关引入准入校验后，`proxy` 在 profile **无** key 时的兜底分支写作 `auth = request.headers.get("Authorization") or ...`——客户端为准入提交的 `GATEWAY_CLIENT_API_KEY` 被原样转发给上游。对 Ollama / TensorRT-LLM 这类不校验认证头、却把请求头写进访问日志的引擎，数据面皇冠密钥会静默溢入不受 modelctl 凭据管理约束的引擎进程日志。
- **根因**："验完即丢"只写进了 `verify_client` 的设计语义，没有落实到**所有**上游头写入路径。keyed profile 分支有 `up_key` 覆盖所以安全，泄露面恰恰藏在"没有 key 可覆盖"的 else 兜底里——安全语义的漏洞通常就在兜底/回退分支。
- **解决方案**：上游 `Authorization` 只允许来自 profile 有效 key，无 key 就**什么都不带**（`proxy`：`if up_key: headers["Authorization"] = ...`，无 else；`anthropic_proxy`：白名单直接不含 `authorization` / `x-api-key`，有 `up_key` 才注入双头）。keyless 引擎本就不看认证头，省掉零损失。
- **通用教训**：声明"某凭据验完即丢/绝不外传"时，须枚举**每一条**可能把它写进下游的路径（含 else/兜底/默认透传分支）并逐一钉死；写"凭据流向图"比凭记忆改主分支可靠。
- **测试钉**：`tests/test_gateway.py::test_proxy_keyless_profile_strips_client_key`（keyless → 上游无 authorization）、`::test_proxy_keyed_profile_uses_profile_key`（keyed → 上游收 profile key）、`::test_anthropic_messages_passthrough`（messages 通道 keyless 双头均剥离）。

## `hmac.compare_digest` 对非 ASCII str 抛 TypeError——须以 UTF-8 bytes 比较

- **日期**：2026-09-07　**分类**：后端 / 网关鉴权
- **现象**：`hmac.compare_digest(a, b)` 两侧都是 str 且任一侧含非 ASCII 字符时**直接抛 `TypeError`**（不是"返回 False"）。密钥比较场景下，若省掉 encode 直接对 str 比较，这会冒泡成 500 而非 401——鉴权函数把"畸形输入"处理成了"服务器故障"。
- **根因与真实机制**：`compare_digest` 对 str 入参要求纯 ASCII，非 ASCII str 属硬错误。candidate 来自外部不可信输入（如 `Authorization: Bearer 密钥`），必须干净拒绝。**正确做法是比较前双方 `.encode("utf-8")` 转 bytes**：bytes 入参无 ASCII 限制，非 ASCII 输入只是编码后字节与期望值不一致，自然走"不匹配"分支返回 `AUTH_INVALID`——这才是主机制。代码里保留的 `try/except TypeError`（`core/gateway.py` L105-108）只是**纵深防御**（headers 混入非 str 等意外类型时兜底为不匹配、不得冒泡成 500），不是非 ASCII 场景的实际拦截路径；沉淀/引用时勿把"靠 try/except 挡非 ASCII"当结论。
- **解决方案**：统一 `hmac.compare_digest(candidate.encode("utf-8"), expected.encode("utf-8"))` 范式，与 `core/cluster/tokens.py::token_matches`（candidate 来自 worker 上报的不可信输入）同型；比较前先判空 fail-closed。
- **测试钉**：`tests/test_gateway.py::test_verify_client_non_ascii_rejected`（`Bearer 密钥` 断言返回 `invalid` 而非异常/500）。

## SSE 场景不可用 BaseHTTPMiddleware 做鉴权——处理器首行显式调用

- **日期**：2026-09-07　**分类**：后端 / 网关鉴权
- **现象/风险**：给网关加鉴权时"顺手"用 `app.middleware("http")`（BaseHTTPMiddleware）看似最省，但本项目网关对 SSE 生命周期是**手工管理**的：`core/gateway.py` `proxy` 内注释明确（L944-946）——不能用 `async with` 包裹后返回 `StreamingResponse`，客户端会在端点返回时立即关闭，而 SSE 是惰性迭代的，真实 uvicorn 下连接会被提前切断；httpx 客户端非流式读完即关、流式由生成器在迭代结束后 `aclose()`。BaseHTTPMiddleware 会在响应体外再包一层任务编排，给这条已验证脆弱的流式链路引入未验证的缓冲/切断风险。
- **解决方案**：不用中间件，三个路由处理器**首行显式调用** `verify_client()`（`proxy` / `anthropic_proxy` / `list_models`）。只有 3 个处理器，显式调用覆盖可枚举、天然不误伤 `/admin/api/*` 与 SPA，且新增路由时"漏调"比"中间件意外拦流"更易在测试中暴露（每个处理器的 401 用例各钉一条）。
- **通用教训**：凡是端点里有"手工管理的外部资源生命周期"（流式响应、长连接、生成器内 close），加横切逻辑前先确认横切框架不会提前终结响应体；宁可显式重复，不要隐式拦截。

## Ollama / TensorRT-LLM 引擎侧无鉴权能力——只能 nginx + 网关两层兜底

- **日期**：2026-09-07　**分类**：后端 / 网关鉴权
- **现象**：给引擎层补 `--api-key` 时排查发现，vLLM/llamacpp/SGLang/Aphrodite/TokenSpeed 都能经基类 `engines/base.py::api_key_args()` 下发 key，LMDeploy 不走基类但自带手写的 `--api-keys`（复数）flag 等价下发——唯独 Ollama 与 TensorRT-LLM 加不上——`engines/ollama.py::build_command` 与 `engines/tensorrt_llm.py::build_command`（venv/docker 两分支）均未调用 `api_key_args()` 也无等价逻辑，这不是漏配而是官方无能力。
- **官方口径**：Ollama 明确"No authentication is required when accessing Ollama's API locally"（docs.ollama.com/api/authentication），本地 API 无认证概念；trtllm-serve 参数表无 `--api-key`（NVIDIA TensorRT-LLM 官方文档）。强行传未知 flag 只会启动失败。
- **解决方案**：这两类引擎的准入完全依赖前两层——网关路径由网关 `verify_client` 把守；模型直连路径由 nginx `$llm_reject_all` 白名单把守（`docs/nginx/llm-routing.example.conf` location 4 注释：本 location 不改写 Authorization，Ollama/TRT-LLM 引擎侧无鉴权，这一层是它们唯一的准入闸门；白名单生成见 `core/nginx_snippet.py::build_client_auth_map`）。
- **通用教训**："三层加固"不是每个引擎都三层齐全——评估安全性时须逐引擎核对能力矩阵（权威口径是看 `engines/*.py` 是否消费 `api_key_args()` **或自带等价 key 下发逻辑**——如 LMDeploy 手写 `--api-keys`、unsloth 自管运行时 key，都不走基类但确有 key），勿误以为"引擎层加了 key 就安全"；对无能力的引擎，nginx 片段漏传/配漏就是裸奔。
