# 启动进度与日志可观测性

> 本文件为「模型启动进度可视化」计划（2026-09-08）沉淀问题的聚合入口；原始单文件已并入本文件归档以保留溯源信息。

## docker run --detach 路径下 launch log 只有容器 ID，SSE / CLI logs / 早退摘录全废

- **日期**：2026-09-08　**分类**：后端 / 日志

### 根因

vllm/tokenspeed/tensorrt_llm 走 docker runtime 时，启动命令是 `docker run --detach`：客户端进程秒返回，stdout 只打印一行**容器 ID**，容器的真实引擎输出（banner、权重加载、报错栈）全部留在 **daemon 侧**，`launch-<name>.log` 里根本没有。连锁失效面：

1. 详情页日志 SSE（`GET /admin/api/models/{name}/log/stream`）尾随的是 launch log —— 镜像拉完前整个日志窗口只有容器 ID 一行；
2. `modelctl logs` / CLI 早退时的 `log_excerpt()` / `tail_file(log, 50)` 摘录同样只能截到容器 ID，进程早退排障形同盲查；
3. loading 段引擎日志模式表（`startup_progress.PATTERNS`）依赖 banner 行做进度锚点，日志缺失则进度永远推不动。

### 解决方案

启动后挂一个独立的**日志 tee 子进程** `docker logs -f --tail all <container>`，把容器输出续写（append）到 launch log：

- **`--tail all` 而非 `--tail 0`**：`docker run --detach` 秒返回，tee 挂上前有数百毫秒窗口，只跟新行会漏掉 banner 首行，伤及模式表匹配；launch log 此前只有一行容器 ID，全量重放无副作用，重复行由 watcher 的 pct 单调不减兜住。
- **append（`"ab"`）+ 独立 PID 文件** `<name>.log-tee.pid`：docker 路径不写引擎 PID（`write_pid=not is_docker`），tee 生命周期必须与引擎 PID 解耦。
- **start 前先清残留 tee**（`start_profile` 开头 `kill_log_tee`）：上一次 start 未走完 / 容器被外力杀时 tee 可能仍在跟随旧容器，双 tee 会重复写同一 launch log。
- **stop / 就绪失败时 kill**：容器被删后 `docker logs -f` 会自行退出，但主动 kill 保证 PID 文件与句柄即时释放。

### 代码示例

```python

    tp = tee_pid_file(name)          # cache/<name>.log-tee.pid，与引擎 PID 分离
    if tp.is_file():                 # 先清残留 tee，防双写同一 launch log
        ...kill_pid_tree(old); tp.unlink(missing_ok=True)
    path = launch_log(name) or (log_dir() / f"launch-{name}.log")
```

## 长启动静默导致误判"卡死"并人为重试杀掉慢而正常的冷启动（Exit 137）

- **日期**：2026-09-08　**分类**：后端 / 引擎启动

### 根因

docker 冷启动（pull 大镜像 + WSL2 内首次加载权重）可达 15 分钟，而旧实现在整个窗口内**零输出**，三个断点叠加：

1. `docker_setup.ensure_image()` 旧版用 `subprocess.run(["docker", "pull", image], capture_output=True)`——pull 的逐层进度全被吞进内存，只在整个 pull 结束后才可能出现在错误文案里，拉一个 20GB 镜像期间 CLI/WebUI 完全静默；
2. `start_profile`（旧 `_do_start`）从拉镜像到健康检查全程不发任何阶段事件，WebUI 只能干转圈；
3. 健康检查超时缺省 600s 对 docker 冷启动不够用，用户/编排层误判"卡死"后重试或强杀，`docker rm -f` 给本在正常加载的容器记 Exit 137——**慢而正常的启动被人为杀死**。

### 解决方案

- **5 段阶段机**：`STAGES = ("preflight", "prepare_env", "launch", "loading", "health")`（`core/startup_progress.py`）。`StartupTracker` 在每个阶段 `begin/progress/done/fail`，双通道输出：`on_progress` 回调（CLI 打单行日志、WebUI 经 `call_soon_threadsafe` 桥到任务 SSE 的 `stage` 帧）+ 快照文件 `cache/<name>.startup.json`（页面刷新/非发起者浏览器轮询 `GET /admin/api/models/{name}/startup` 兜底）。
- **prepare_env 段接 PullParser**：`ensure_image()` 改 `Popen` 流式逐行读（stderr 并入 stdout），每行喂 `PullParser.feed()` 聚合为 [0,1] 总进度回调 `on_progress(label, pct)`；重试前 `parser.reset()`（docker 复用已下载 layer，pct 从当前已完成数重算属真实语义）。
- **loading 段接 LoadingWatcher**：daemon 线程 tail launch log（窗口 400 行），按引擎 `PATTERNS` 模式表（vLLM banner / `Downloading shards` / `Loading safetensors checkpoint shards` / `Capturing CUDA graph shapes` 等）推进子进度；**静默（无新增进展，含日志尚未生成窗口）超 120s → 发兜底文案**「引擎初始化中（首次冷启动在 docker/WSL2 上可达 15 分钟）」，`pct=None` 触发前端条纹动画。
- **超时自适应**：`default_start_timeout()`——`MODELCTL_START_TIMEOUT` 环境变量优先，docker runtime 用 `START_TIMEOUT_DOCKER = 1800`，其余 `START_TIMEOUT_DEFAULT = 600`。
- 阶段耗时按 `engine:stage` 落 `cache/startup-timing.json`（EMA），给出各阶段 ETA。

### 代码示例

## docker runtime 下 WebUI `<pre>` 只显示容器 ID + 「vllm」镜像名，fallback 容器日志

- **日期**：2026-09-09　**分类**：后端 / 前端 / 日志

### 根因

`docker run --detach` 客户端秒返回，`launch-<name>.log` 只有一行**容器 ID**（64 位十六进制）+ 镜像名（如 `vllm/vllm-openai:latest` 或 `vllm/vllm-openai:v0.7.0`），容器内真实引擎日志（banner / `INFO: vLLM starting` / ERROR 栈）全部留在 daemon 侧 → `<id>-json.log` / `docker logs`。

即使已有 `spawn_log_tee`（`docker logs -f --tail all` 续写到 launch log），仍有以下断点使 WebUI `<pre>` 退化为容器 ID 单行：

1. **原 SSE 流**（`admin_models.py:_sse_log_stream`）按 `launch-<name>.log` 的字节 offset 推增量——容器刚拉起时 tee 子进程还没追上、或容器还没产出 stdout，launch log 一行不动 → 前端拿到的就是 `<pre>` 渲染出来的固定两行（容器 ID + `vllm`）；
2. **GET /log** 同样只读 launch log 尾部——首屏预填充（`refreshLog`）与"拉取最新"按钮都基于此 → 切详情页同框断点。

### 解决方案

在 `admin_models.py` 新增 4 个 helper + 改 SSE / GET 端点，**docker runtime 自动 fallback 容器日志**：

1. **`_launch_log_effective(lines)`**：复用 `all_service._CONTAINER_ID_LINE`，判定 launch log 是否含有效内容（≥1 行非容器 ID 短词且非 `vllm` 短词）；
2. **`_read_docker_logs(name, tail)`**：`docker logs --tail <N> <container>` 按需拉，异常静默；
3. **`_tail_from_launch_log(name, lines)`**：统一 launch log 尾部读取（避免端点重复写）；
4. **`docker_core_log_path(name)`**：`docker inspect --format {{.LogPath}}` 取容器内 `<id>-json.log` 绝对路径（dockerd 持久写的 json 行日志）；
5. **`_docker_json_line_text(entry)`**：单行 JSON 提取 `log` 字段（docker 一行 = 一次 write syscall，`log` 以 `\n` 结尾，strip 后即 `<pre>` 行文本；解析失败整行透传）。

**端点行为**：

- `GET /admin/api/models/{name}/log`：先读 launch log，**有效直接返回**；无效（仅容器 ID + vllm）→ `docker logs --tail <lines>`，仍空则返回 launch launch 原行；
- `GET /admin/api/models/{name}/log/stream`（SSE）：launch log 无效时，首连接 dump 一次 `docker logs --tail 200` + 记 `<id>-json.log` 当前 `st_size`，**后续每 2s 按字节 offset 推 json.log 增量**（容器存活时新行即推）。文件消失（容器删 / daemon 重启）→ 发 `event: stopped` 帧 + `return`，前端置 closed；
- **前端 `sse.ts`** 注册 `stopped` 命名事件，data 解析 `reason` 字段；`SseLogViewer` 在 `onStopped` 回调里追加「（日志流已停止：<reason>）」行并置 `state=closed`；
- **前端 `ModelDetailView.vue`** 5s 轮询在 `tab==='log'` 时同步调 `refreshLog()`，对 `docker-in-docker` / 容器删后 SSE `stopped` 兜底。

### 代码示例

## EventSource 无首行日志时前端永显「连接中…」（open 事件 + 挂载时机双断点）

- **日期**：2026-09-08　**分类**：前端 / SSE

### 根因

`SseLogViewer.vue` 的状态机是 `connecting → open → closed`，但 `state` **只在 `onLine` 回调里翻转为 `open`**。docker 路径启动初期 launch log 尚无新行（或流刚建立、后端 2s 轮询还没轮到新字节）时，一条 `log` 帧都收不到，状态灯永远显示「连接中…」——实际流早已连通。两个断点：

1. `api/sse.ts` 从未注册 EventSource 的 `open` 事件，传输层"已连接"信号被丢弃（`open` 在首个响应到达即触发，与有无数据帧无关）；
2. 组件在 `v-if` 下挂载时 `props.url` 恒定不变，`watch(url)` 永不触发，`open()` 根本没有调用点——建流时机也缺失。

### 解决方案

- `openModelLogStream()` 增加 `onOpen` 钩子并 `addEventListener('open', ...)`（close 时对称 `removeEventListener`）；后端命名事件 `log` / `heartbeat` 也各自 `addEventListener` 注册（`onmessage` 只派发无名帧）。
- `SseLogViewer.vue` 状态翻转改由 `onOpen` 驱动：`if (state.value === 'connecting') state.value = 'open'`；同时 `onMounted(open)` 保证挂载即建流。

### 代码示例

## docker logs -f 一次性 tee 断流 → loading 进度永远卡死，需保活 supervisor 重连

- **日期**：2026-09-09　**分类**：后端 / 引擎启动 / 日志

### 根因

`spawn_log_tee` 挂载的 `docker logs -f --tail all <container>` 是**一次性子进程**：只要它因任何原因退出（docker CLI 崩溃、daemon 短暂不可达、WSL2 网络抖动、被外力杀），容器输出就**永远不再回写** launch log。连锁失效面（以 qwen2.5-0.5b-vllm 实测为证）：

1. LoadingWatcher tail 的是 launch log，tee 断流后匹配不到任何 vLLM 进度行（banner / 下载权重 / 加载权重 / CUDA graph），**进度永远卡在「加载模型」**，只剩 120s 兜底文案 + 前端条纹动画；
2. WebUI 日志 `<pre>` / SSE / CLI 早退摘录同样只拿到断流前的行——排查时看不到容器真实输出；
3. `modelctl.webui` 的 docker logs fallback（`admin_models`）虽有兜底，但 loading 段的进度上报走的是 launch log，二者脱节。

**实测**（qwen2.5-0.5b-vllm）：tee 进程（PID 20376）已死亡，`docker ps CreatedAt 16:35:16`，容器在 16:46:01 才输出首条 vLLM banner —— 这 10 分 45 秒的**静默期**内 tee 早已断流，容器实际输出全部滞留在 daemon 侧，launch log 只有一行容器 ID，进度上报与真实引擎状态完全脱节。

### 解决方案

把 `spawn_log_tee` 从「直接 Popen `docker logs -f`」改为「spawn 一个**保活 supervisor** 子进程」（`python -m modelctl.core.process --log-tee <container> <launch-log>`），由 supervisor 循环续写并**自动重连**：

- **首轮 `--tail all`**：重放容器已有历史（含 tee 挂上前数百毫秒的 banner，保住 loading 模式表锚点）；
- **重连轮 `--tail 0`**：docker logs 异常退出且**容器仍存活**时，以 `--tail 0` 只跟新行续写——避免全量重放使 launch log 无限膨胀、并挤占 LoadingWatcher 的 tail 窗口漏掉后续真实进度行；
- **退出条件**：`docker_container_alive` 为 False（容器已删/已退出，引擎结束无需续写），或被 `kill_log_tee` / `kill_pid_tree` 终止（stop / 换容器场景）；
- **退避**：断裂后 3s 起步、指数退避、上限 30s；每次重连往 launch log 写一行 `[docker-log-tee]` 痕迹便于排查。
- `.log-tee.pid` 仍指向 supervisor 进程，`kill_log_tee` 语义不变（杀进程树即连 docker logs 子进程一并终止），跨进程 stop 依旧成立。

### 代码示例

```python
# ✅ src/modelctl/core/process.py —— spawn supervisor（替代一次性 docker logs -f）
def spawn_log_tee(name: str, command: list[str]) -> int | None:
    ...  # 清残留 tee
    container = command[-1]                     # ["docker","logs","-f","--tail","all",<container>]
    cmd, env = _log_tee_supervisor_cmd(container, path)
    proc = subprocess.Popen(cmd, env=env, stdout=subprocess.DEVNULL,
                            stderr=subprocess.DEVNULL, stdin=subprocess.DEVNULL,
                            start_new_session=True)
    tp.write_text(str(proc.pid), encoding="utf-8")

def _log_tee_supervisor(container, log_path, retry_sec=3.0) -> None:
    tail = "all"
    while docker_container_alive(container):
        with open(log_path, "ab") as fp:
            p = subprocess.Popen(["docker", "logs", "-f", "--tail", tail, container],
                                 stdout=fp, stderr=subprocess.STDOUT,
                                 stdin=subprocess.DEVNULL, start_new_session=True)
            p.wait()
        if not docker_container_alive(container):
            return
        _write_tee_reconnect(log_path, ...)     # 一行 [docker-log-tee] 痕迹
        time.sleep(retry_sec)
        tail = "0"                              # 只跟新行，不全量重放
```
