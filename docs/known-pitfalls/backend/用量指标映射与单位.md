# 用量指标映射（引擎 gauge → stats → /api/usage）

> 2026-09-10：沉淀扩充 vLLM 指标映射时发现的两个静默缺陷——映射白名单丢弃新增键、直方图均值未换算单位。

## 引擎声明的扩展指标被 `parse_metrics` 白名单静默丢弃

**日期**：2026-09-10
**症状**：给 `vllm.metrics_mapping()` 加了 `waiting` / `kv_cache_usage` / `preemptions_total` 等键，`/metrics` 里也确实有这些 gauge，但 `/api/usage` 与快照里始终看不到——不报错、不告警，就像没配。

**根因**：`stats.parse_metrics()` 用一份**固定五键白名单**初始化结果字典，再用 `{k: v for k, v in mapping.items() if k in result}` 过滤 mapping。引擎声明的任何新键在这一步就被滤掉，之后 `_snapshot` / `_poll_once` / `snapshot()` 三处又各自用**字面量 dict** 重建快照——即便解析层放行，快照层也会再丢一次。两层都是"新增键必须同步改代码"，而改的人只看到映射表这一层。

**解决方案**：

- `parse_metrics` 改为「核心键（`CORE_METRIC_KEYS`）恒存在 + `mapping` 声明的键 `setdefault` 全部保留」；
- 快照侧不再逐键铺字面量：`UsageCollector.__init__` 用 `self._extra_keys = tuple(k for k in self.mapping if k not in CORE_METRIC_KEYS)`，轮询成功/异常两条分支统一写进 `engine_metrics` 子字典；
- `/api/usage` 双出口：`extra` 文本追加一段（只报异常侧：有排队 / KV>50% / 有抢占 / 有命中 / 排队耗时），结构化 `engine_metrics` 仅在**非全 0** 时下发，避免非 vLLM 引擎多出一屏空值。

**教训**：

- **可扩展的映射表配一份硬编码消费清单 = 配了不生效且不报错**。加映射能力时，消费侧必须按 mapping 驱动，而不是反过来让映射表迁就消费侧的枚举。
- 同一份数据在链路上被**多处重建**（解析 → 轮询 → 快照 → HTTP 响应）时，加字段要**沿链路逐层走查**，漏一层就等于没加。
- 新增可选指标要钉"无该 mapping 的引擎不引入任何新键"的用例，否则老引擎响应体莫名膨胀。

## 直方图均值写进 `_ms` 键漏了秒→毫秒换算，TTFT 恒显示 0 ms

**日期**：2026-09-10
**症状**：走 gauge 轮询（非主动测速）的 vLLM target，`/api/usage` 的 `extra` 里首 Token 耗时永远渲染成「首 Token P50 = 0 ms」，而同一个模型走 bench 兜底时显示正常的一百多毫秒。

**根因**：vLLM 的 `vllm:time_to_first_token_seconds` 是 Histogram，只有 `_sum` / `_count`，没有裸名 gauge。`parse_metrics` 的兜底分支用 `_hist_mean()`（= `sum/count`）填进 `ttft_ms` 键，但 **`_hist_mean` 返回的是秒**（2.5/10 = 0.25 s），`ttft_ms` 键承诺的是**毫秒**。`0.25 > 0` 所以照常进入渲染，`round(0.25)` = 0，最终输出「首 Token P50 = 0 ms」。

**解决方案**：把直方图兜底从"仅 `ttft_ms`"泛化为「**任意以 `_ms` 结尾的键**」（`e2e_ms` / `queue_ms` / `prefill_ms` / `decode_ms` 同病同治），换算统一交给 `_to_ms_factor(metric_name, key)`。

**换算判据是指标名的单位后缀，不是"走的是哪条分支"**：早先只给直方图分支补了 `* 1000.0`，裸名 gauge 分支仍按原值写入，形成"同一条链路上两条路径两种量纲"。后来抽出 `_to_ms_factor` 让**两条分支共用**——裸名 `vllm:time_to_first_token_seconds 0.3` 与直方图均值一样得 300.0。对 vLLM 这条链路裸名分支是死分支（`prometheus_client` 的 Histogram 不导出裸样本），所以补测试时是用「将来接入的引擎输出 `_seconds` 裸 gauge」这一口径钉住的，而非依赖 vLLM 现状。

三个设计细节：

- **先按 key 把关**：`if not key.endswith("_ms"): return 1.0`。吞吐率 gauge `vllm:prompt_tokens_seconds` 名字也以 `_seconds` 结尾（语义是"每秒 token 数"），只靠指标名会把它 ×1000。
- **倍率由纳秒数推导**，不手写十的幂：`_UNIT_SUFFIX_TO_NS` 存「该单位等于多少纳秒」，返回 `ns / _NS_PER_MS`。手写过一遍就把纳秒→毫秒写成了 `1e-6`（那是纳秒→微秒），错一档的结果仍"看着像个数"，比漏换算更难发现。
- **无单位后缀保守返回 1.0**：漏乘让数值偏小（会被当成"没流量"而暴露），误乘 1000 会造出一个以假乱真的延迟值，两害相权取前者。

**教训**：

- **键名里的单位是契约**。`_ms` / `_bytes` / `_ratio` 后缀必须由写入侧负责兑现，兜底路径最容易漏——因为它是"另一条代码路径"。
- 修一个分支时**立刻找同函数的同构分支**：只补一条路径等于把"分支间量纲不一致"这种更隐蔽的问题固化下来。正确做法是把换算抽成小函数，让所有写入点共用。
- 派生值（sum/count、比率、差分）与直接取值走的是不同分支时，**两条分支的单位/量纲要各自核对**，不能假设兜底"照抄就行"。
- 这类 bug 用"显示 0"的形式呈现，很容易被当成"这台机器没流量"而放过去。渲染处 `if val > 0` 的静默省略会掩盖上游的单位错误——排查时应该直接看**原始数值**而不是渲染文本。
- 修单位后**必红**的既有断言（本例 2 处 `== 0.25`）是好事：说明它们真的在钉这个值。改断言时把"为什么现在是 250"写进用例 docstring，避免后人以为是随手放宽。同理，`test_parse_metrics_ttft_prefers_bare_gauge` 从 `== 0.3` 改成 `== 300.0` 时要在 docstring 里写清「prefer bare 指取值优先级，不是免换算」，否则看起来像把这条用例的意义改掉了。

## vLLM V1 指标改名与"命中率 gauge 已弃用"，候选名列表要按新名优先

**日期**：2026-09-10
**症状**：老配置里用 `vllm:gpu_cache_usage_perc` 取 KV cache 占用，升级到 V1 指标后取不到值；想用 `vllm:prefix_cache_hit_rate` 看命中率，新版根本没有这个 gauge。

**根因**：

- KV cache 占用在 V1 里叫 `vllm:kv_cache_usage_perc`（**0–1 的分数，不是百分数**），`gpu_cache_usage_perc` 是旧名；
- 抢占计数 V1 是 `vllm:num_preemptions_total`（Counter），旧名 `vllm:num_preemptions`；
- prefix cache 只留 `vllm:prefix_cache_queries` / `vllm:prefix_cache_hits` 两个 Counter，**命中率 gauge 已被官方弃用**——官方口径是 `rate(hits)/rate(queries)`，由消费方自算。

**解决方案**：`metrics_mapping()` 每个键给**候选名列表**，新名在前、旧名兜底（首个命中即生效）；命中率在 `stats._derive_engine_metrics()` 里由 `hits/queries` 现算。

**教训**：

- 映射表设计成 `list[str]` 候选名（而非单个 `str`）是对的，版本改名只需追加一项，消费侧零改动。
- **累计 Counter 相除得到的是"自启动以来的平均命中率"**，平滑但滞后；它能看趋势，不能当瞬时值用。派生这类指标时把口径写进注释，否则会被误读成"这一分钟的命中率"。
- 引第三方引擎的指标名前务必查**当前锁定版本**的官方文档：名称、类型（Gauge/Counter/Histogram）、量纲（0–1 还是 0–100）三项都可能与记忆中的旧版不同。
