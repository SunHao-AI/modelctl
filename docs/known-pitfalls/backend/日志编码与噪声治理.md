# 日志编码乱码与噪声治理

> 本文件为 data/logs 日志乱码修复与冗余日志降级（2026-09-08）沉淀问题的聚合入口；原始单文件已并入本文件归档以保留溯源信息。

## loguru 的 Windows `TERM` 特判把 ANSI 色码写进重定向文件，日志满屏 `←[31m` 乱码

- **日期**：2026-09-08　**分类**：后端 / 日志

### 根因

`data/logs/launch-llm-gateway.log`、`launch-usage-stats.log` 等文件里出现大量 `←[31m`、`←[0m` 之类的字符。这不是编码问题，而是 **ANSI 转义色码被原样写进了文件**。

loguru 在 `loguru/_colorama.py` 的 `should_colorize(stream)` 里的判定顺序是：

```python
# loguru/_colorama.py（实际源码，L24-38）
if stream is sys.__stdout__ or stream is sys.__stderr__:
    if "CI" in os.environ and any(ci in os.environ for ci in [...]):
        return True
    if "PYCHARM_HOSTED" in os.environ:
        return True
    if os.name == "nt" and "TERM" in os.environ:   # ← 元凶
        return True
try:
    return stream.isatty()
except Exception:
    return False
```

两个致命点：

1. `TERM` 特判**排在 `stream.isatty()` 之前**，重定向与否完全不参与判断。
2. 整个函数**从头到尾不读 `NO_COLOR`**——loguru 根本不支持这个约定。

于是只要进程环境带 `TERM`（Git Bash / MSYS 启动的父进程会把 `TERM` 继承给子进程）或带 `PYCHARM_HOSTED`，loguru 就无条件把 ANSI 码写进已经重定向成文件的 stderr。

### 解决方案

- **绝不把 colorize 交给 loguru 自动探测**：在 `core/logging.py` 的 `setup_logging()` 中显式传入 `colorize=_console_colorize()`，其值仅由项目自身的颜色开关（`core/colors.py` 的 `color_enabled()`：`FORCE_COLOR` > `NO_COLOR` > `MODELCTL_NO_COLOR` > `TERM=dumb` > `CI` > `sys.stdout.isatty()`）决定。后台服务经 `start_detached` 后 stdout/stderr 都是文件，`isatty()` 为 False ⇒ 自然无色。
- 文件 sink（`modelctl.log`）不传 `colorize`（loguru 对文件默认不上色），格式串也不得内嵌颜色标签。

### 代码示例

```python
# ✅ src/modelctl/core/logging.py
def _console_colorize() -> bool:
    """显式决定，绝不交给 loguru 自动探测（TERM 特判会把 ANSI 写进文件）。"""
    return color_enabled()

logger.add(sys.stderr, level=level, format=_build_console_format(),
           colorize=_console_colorize())
```

```python
# ❌ 反例：把 colorize 留给 loguru，Windows + TERM 环境下重定向文件必染 ANSI
logger.add(sys.stderr, level=level, format=...)
```

- **验证方式**：设 `TERM=xterm` 后把 stderr 重定向到文件，用字节扫描统计 `\x1b`（ESC）计数应为 0，中文正常显示。

## 子进程 stdio 重定向到文件时编码回退 locale（中文 Windows = GBK），UTF-8 读取全乱码

- **日期**：2026-09-08　**分类**：后端 / 子进程

### 根因

`launch-modelctl-webui.log` 用 UTF-8 打开是乱码，用 GBK 反而能正确解码。原因：Python 进程的 stdout/stderr 编码在**连接到管道/文件时回退到 locale 编码**（中文 Windows 即 GBK/cp936），而非 UTF-8；只有连 TTY 时才（3.6+ 默认）UTF-8。`start_detached()` 把所有后台服务的 stdout/stderr 直接重定向到 `launch-<name>.log`，于是子进程打印的中文全部以 GBK 字节落盘，与项目"日志统一 UTF-8"的约定冲突（文件 sink 侧 `encoding="utf-8"` 只管 loguru 自己写的部分）。

### 解决方案

- 在 `core/process.py` 的 `start_detached()` 构造子进程环境时**恒定注入** `PYTHONIOENCODING=utf-8`，且放在字典合并的**最后**，保证既不会被父环境缺失影响、也不会被 `extra_env` 覆盖：

### 代码示例

```python
# ✅ src/modelctl/core/process.py（start_detached 内）
env = {**os.environ, **subprocess_timezone(), **extra_env,
       "PYTHONIOENCODING": "utf-8"}  # 置末位：恒定生效，不可被覆盖
```

```powershell
# ❌ 初版把 PYTHONIOENCODING 放在 **extra_env 之前，可被调用方覆盖而失效
env = {**os.environ, "PYTHONIOENCODING": "utf-8", **subprocess_timezone(), **extra_env}
```

- **验证方式**：`start_detached` 起一个探针子进程打印 `sys.stdout.encoding` 与中文，读取日志原始字节应为 `b'utf-8 utf-8\r\n\xe4\xb8\xad\xe6\x96\x87...'`（UTF-8 字节序列）。

## uvicorn access 日志（心跳轮询 / GET /metrics）刷屏，需要"INFO 静默、DEBUG 恢复"

- **日期**：2026-09-08　**分类**：后端 / 日志

### 根因

`launch-modelctl-webui.log` 高达 1.7MB/2 万余行，尾部几乎全是前端心跳轮询的 access 行（Dashboard 3s、ModelDetail/ClusterNodes/ClusterGoals 5s 轮询）；`launch-qwen3.8-vllm.log` 则全是 `"GET /metrics HTTP/1.1" 200 OK`。这类**访问日志价值极低但量极大**，淹没有效信息。

两个约束决定了不能简单调 logger level：

1. uvicorn 的 access 记录**级别固定为 INFO**，把 `uvicorn.access` logger 调到 WARNING 会把 4xx/5xx 异常访问也一起丢掉。
2. loguru 与 stdlib logging 是两套体系：gateway/webui/stats 入口此前**根本没接 loguru**，loguru 的 `LOG_LEVEL` 对它们不生效。

（vLLM 侧 2026-08-26 已合入 `--disable-uvicorn-access-log`，旧日志中的 /metrics 刷屏系该参数生效前的部署残留。）

### 解决方案

- `core/logging.py` 提供 `uvicorn_log_config()`：复刻 uvicorn 默认 dictConfig，仅在 `access` handler 上挂一个 `AccessLogDebugFilter`——`LOG_LEVEL` 为 DEBUG/TRACE 时放行，否则拦截。语义等价"access 日志 = DEBUG 级"，而 4xx/5xx 仍由 `uvicorn.error` 保留。
- gateway / webui / stats 三个子进程入口统一接入 `setup_logging(file_sink=False)`（后台进程**不得**再写 `modelctl.log`，多进程同文件轮转互踩），`uvicorn.run(..., log_config=uvicorn_log_config())`。
- **dictConfig 的 `"()"` 必须传类对象而不是"module.Class"字符串**：字符串按调用方 `sys.path` 解析，gateway venv 里装有旧版 modelctl 0.3.0 副本，会命中旧实现。

### 代码示例

```python
# ✅ src/modelctl/core/logging.py
class AccessLogDebugFilter(logging.Filter):
    def filter(self, record: logging.LogRecord) -> bool:
        return os.environ.get("LOG_LEVEL", "INFO").upper() in ("TRACE", "DEBUG")

def uvicorn_log_config() -> dict:
    return {
        "version": 1,
        "disable_existing_loggers": False,
        "filters": {"access_debug_only": {"()": AccessLogDebugFilter}},  # 类对象直传
        # ... formatters/handlers 与 uvicorn.LOGGING_CONFIG 一致，
        # access handler 追加 "filters": ["access_debug_only"]
    }

# ✅ 入口（gateway.py / webui/server.py / stats.py 的 main()）
setup_logging(file_sink=False)
uvicorn.run(app, ..., log_config=uvicorn_log_config())
```

```python
# ❌ 字符串形式：按 sys.path 解析，可能命中 venv 里的旧 modelctl 副本
"filters": {"access_debug_only": {"()": "modelctl.core.logging.AccessLogDebugFilter"}}
# ❌ 把 uvicorn.access 调到 WARNING：4xx/5xx 一并丢失
"uvicorn.access": {"level": "WARNING"}
```

- **验证方式**：临时端口起 webui，默认（INFO）下打 6 次请求 → access 行 0 条、无 ANSI；`LOG_LEVEL=DEBUG` 重启 → access 行恢复打印。就绪判定用日志中的 `Application startup complete`，不要用 `GET /health`（webui 未注册该路由，404 不代表未就绪；且 create_app 扫描 profile 在网络盘上可能要几十秒）。
